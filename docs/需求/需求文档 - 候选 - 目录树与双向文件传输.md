## 1. 原始需求点

1. 在终端的顶部添加一个【目录树】按钮，点击后展示对应终端上的目录树；目录树默认折叠，动态加载树节点；终端当前所在目录自动展开。
2. 目录树可以拖动【目录树】按钮到终端页面的左侧、右侧，和终端页面形成分屏。
3. 目录树最好能实时同步终端上的文件。
4. Obsidian 上的所有目录、笔记都能直接拖到目录树，目录树上的所有文件、文件夹也能拖动到 Obsidian 上。
5. 目录树上的节点双击后可以在终端直接进入该目录。

## 2. 背景与核心价值

Termy 目前的文件流动只有一个方向、一种触发方式：从 Obsidian 文件列表把**一篇笔记**拖进终端，落在该终端当前目录（本地模式固定行为不变；v2.0 远程模式落在终端上报的当前目录，见 [需求文档 v2.0 §4](需求文档 v2.0.md)）。用户看不到终端所在文件系统的结构，也无法把终端里的文件带回 Obsidian —— 这在 V1/v2.0 的既有边界中就被明确记录为"不做"（[需求文档.md](需求文档.md) 与 [实现方案 - 开发版.md](../开发/实现方案%20-%20开发版.md) 均把"文件回传、双向同步"列为范围外）。

本需求把这个单向、盲选的拖拽体验，升级为**可视化目录树 + 双向拖拽**：用户能看见终端所在目录结构，能主动挑选任意文件/目录双向搬运，并且这套体验对本地终端和 v2.0 远程终端（连接到 Agent 设备）都应该适用。

## 3. 第一步：用户故事地图

### 3.1 用户目标

1. 不用先在终端里敲 `ls`/`tree` 或盲猜路径，就能直接看到当前终端（本地或远程设备）的目录结构。
2. 把目录树面板摆在自己喜欢的位置（左/右分屏），像资源管理器一样和终端并排工作。
3. 双击目录树中的目录，终端直接 `cd` 过去，不用手动输入路径。
4. 把 Obsidian 里的笔记、附件、整个文件夹拖进目录树对应位置即可送达终端所在的文件系统；反过来，也能把终端所在文件系统里的文件/文件夹拖回 Obsidian vault。
5. 目录树能感知到终端里发生的文件变化（比如执行了 `mkdir`/`rm`/`mv` 之后），不需要手动刷新才能看到最新结构。

### 3.2 核心用户故事

1. 作为在终端里频繁切换工作目录的用户，我希望有一个可视化目录树代替反复输入 `cd`/`ls`，双击就能进入某个目录。
2. 作为习惯把目录树摆在侧边当资源管理器用的用户，我希望这个面板能停靠成分屏，而不是每次都弹出、关闭。
3. 作为需要把整理好的资料从 Obsidian 发到远程设备、或者把远程设备产出的文件带回 Obsidian 整理的用户，我希望双向拖拽都能做到，而不是只能"发过去"。
4. 作为同时开着终端和目录树的用户，我希望目录树里看到的结构和终端里实际的文件系统保持一致，不会因为我在终端里改了文件而看到过时的树。

## 4. 第二步：5W2H

### 4.1 What：做什么

1. 终端标签页顶部新增【目录树】入口按钮。
2. 点击后展示当前这个终端所在设备/目录的目录树：根节点默认折叠，子节点按需（点击展开时）动态加载，不一次性拉取整棵树；该终端当前工作目录对应的路径链路自动展开。
3. 【目录树】按钮本身可拖拽，拖到终端页面左侧或右侧时，与终端区域形成分屏布局（目录树占一侧，终端占另一侧）。
4. 目录树内容随终端所在文件系统的变化保持更新（结构级刷新，定义见 4.7）。
5. 支持双向拖拽：
   - Obsidian 文件列表中的目录/笔记 → 拖到目录树的某个节点，文件/目录被发送到终端所在文件系统的对应路径下。
   - 目录树中的文件/目录 → 拖到 Obsidian，对应内容被写入当前 vault。
6. 目录树节点双击 → 对应终端执行进入该目录（等价于 `cd` 到该路径）。

### 4.2 Why：为什么需要

1. 现有拖拽体验是"盲选"的：用户必须先在终端里手动定位到目标目录，才能让拖入的笔记落在正确位置；目录树让"看得见、点得到"成为可能。
2. V1 和 v2.0 都把"文件回传""双向同步"列为已知但推迟的能力缺口（见 [需求文档.md §?"后续版本"](需求文档.md) 及 [实现方案 - 开发版.md](../开发/实现方案%20-%20开发版.md) 中的排除项），用户在真实使用中反馈需要这个能力，是时候纳入需求采集。
3. 远程场景（v2.0 已支持连接到 Agent 设备）下，用户很难对着一个黑屏终端凭空判断"这台设备现在长什么样"，可视化目录树能显著降低远程操作的认知负担。

### 4.3 Who：谁使用及权限

1. 面向所有 Termy 用户，本地终端和 v2.0 远程终端场景最终都要覆盖，但分两阶段交付、先本地后远程（见 4.8、6.2）。
2. 远程场景下的目录树浏览、双向传输，安全模型应沿用 v2.0 已确立的"持有连接码即可操作该设备"的信任边界（见 [需求文档 v2.0 §4.3](需求文档 v2.0.md)），不新增额外的路径级权限控制，除非用户明确要求（对应 v2.0 迭代计划里本就列为待评估的"更细粒度连接码权限"）。

### 4.4 When：何时触发

1. 用户点击终端顶部的【目录树】按钮时展开面板；再次点击或关闭时收起。
2. 目录节点被点击展开时才拉取其子节点（懒加载），而非打开面板即拉取整棵树。
3. 终端当前目录变化时（比如执行了 `cd`），目录树中对应路径的展开状态随之更新到新的当前目录。
4. 用户发起拖拽（vault → 树，或树 → vault）时触发一次文件传输/写入。
5. 用户双击目录节点时触发一次"进入该目录"操作。

### 4.5 Where：页面与位置

1. 入口在每个终端标签页的顶部工具栏，新增一个按钮，与现有终端顶部控件（如分屏、锁定等）并列。
2. 目录树默认以可拖拽悬浮/停靠面板的形态出现；拖到终端区域左侧或右侧时转为分屏布局的一侧。
3. 与 Obsidian 之间的拖拽以 Obsidian 原生文件列表（左侧文件浏览器 / 文件标签页）为对端；目录树自身的分屏用 Termy 视图内部自绘的可拖拽分隔条实现，不依赖 Obsidian 原生窗格拆分（理由见 6.3）。

### 4.6 How：交互与实现边界

1. 目录树的数据来源：本地终端直接读取本机文件系统；远程终端需要新增协议能力（列目录、监听变化），当前 v2.0 协议只支持"上报当前目录"和"接收笔记附件"，不支持"浏览任意路径"和"文件系统变化通知"，这是本需求相对 v2.0 最大的协议新增点。
2. 双向拖拽复用 v2.0 已有的"内容寻址、分块校验"传输机制（[需求文档 v2.0 §4.6](需求文档 v2.0.md)），新增的是"树 → Obsidian"这个此前完全没有的回传方向。
3. 双击进入目录：对本地终端等价于在当前 shell 里执行 `cd <path>`；对远程终端等价于向该终端会话发送 `cd` 并等待其 shell 集成上报新的当前目录确认（复用 v2.0 已有的 cwd 上报机制）。
4. 目录树默认折叠、按需加载子节点，避免一次性遍历大目录树；根节点到当前目录的路径链路在打开面板时自动展开一次。

### 4.7 How much：规模与性能

1. "实时同步"采用**轻量定义**：目录树随文件系统变化自动刷新结构（新建/删除/重命名节点），不做文件内容级别的持续双向同步。理由见第 6.1 条。
2. 大目录（数千级子项）不要求一次性渲染，懒加载 + 虚拟滚动即可；具体分页/节流阈值留给开发版给出，不在需求阶段承诺数字。
3. 远程场景下"列目录"和"监听变化"经网络传输，弱网下允许有可感知的延迟（不要求秒级），但不能因为监听通道阻塞而影响该终端本身的正常输入输出；断线时目录树标注"未同步"而非报错崩溃。

## 4.8 分阶段交付

鉴于本地与远程两种场景对协议的依赖程度差异很大（见 6.2），建议分两个阶段交付，而不是等远程协议就绪后一起发布：

- **阶段一（本地终端）**：目录树入口、懒加载、当前目录自动展开、双击 `cd`、面板可拖拽分屏、与 Obsidian 的双向拖拽，全部基于本机文件系统（`fs.watch` 或等价能力），不依赖任何新协议，可独立验证 UI/交互设计。
- **阶段二（v2.0 远程终端）**：在 v2.0 协议中新增"列目录"与"监听目录变化"两类消息，把阶段一验证过的同一套前端组件接到远程 Agent 数据源上；远程目录浏览与回传遵循与阶段一相同的交互，仅数据来源不同。

两阶段共享同一套前端组件与交互设计，阶段一产出即是阶段二的直接基础，不是推倒重来。

## 6. 关键决策（默认方案，评审时可推翻）

1. **"实时同步"的粒度 → 结构级自动刷新，不做内容级同步**。理由：内容级双向同步（类似 Syncthing）需要冲突检测、合并策略、持久化同步状态，这是一个独立量级的项目；而用户描述的核心诉求是"目录树别过时"，结构级文件监听已经满足。内容级双向同步作为更远期的独立需求，不纳入本次范围（对应边界图中的 O1）。
2. **本地与远程的优先级 → 分两阶段，先本地后远程**（见 4.8）。理由：本地不需要新协议，能最快验证目录树本身的交互设计（懒加载、拖拽、分屏）是否好用；远程需要新增协议能力，放在验证过交互之后风险更低，也避免把 UI 设计和协议设计耦合在一起返工。
3. **分屏的实现方式 → Termy 视图内部自绘可拖拽侧栏，不复用 Obsidian 原生窗格拆分**。理由：用户描述的是"拖动【目录树】按钮"这种应用内手势，而不是把目录树做成独立的 Obsidian 视图/叶子再依赖 Obsidian 的工作区分屏；自绘侧栏能精确控制"默认折叠、可停靠左右"的行为，也更贴近现有 Termy 分屏（终端内部左右分屏）已经采用的自绘模式，实现路径一致。
4. **回传方向的落盘规则 → 默认落在 Obsidian 当前激活的文件夹（无激活文件夹时落 vault 根目录），保留被拖拽项在远端的相对目录结构；同名冲突默认不自动覆盖，弹出确认或自动重命名**。理由：发送方向（vault → 终端）同名覆盖是因为目标是工作目录、临时性强；回传方向（终端 → vault）目标是用户的知识库，误覆盖笔记的代价更高，因此两个方向的覆盖策略刻意不对称。
5. **远程目录浏览的信任边界 → 不额外限制，与 v2.0 现有信任模型一致**：持有连接码即可通过终端执行任意命令，因此限制目录树只能看某个子目录并不能提升安全性（用户仍可在终端里 `cd`/`ls` 到任何有权限的路径），只会让 UI 出现"终端能到但树看不到"的不一致体验。若未来做连接码分级权限（v2.0 §7.4 已列为待评估项），目录树应随之继承那套权限，而不是单独发明一套。
6. **版本归属 → v2.1**，与 [需求文档 v2.0 §7.3](需求文档 v2.0.md) 的"可靠性与体验完善"并行、但作为独立工作项排期（不是该节原有范围的扩写），因为体量和性质（新增大面板 + 新协议能力）都超出"打磨"级别的改动。

## 7. 验收清单

1. 用户能在终端顶部打开目录树，看到该终端当前目录已自动展开，未展开的目录点击后才加载子节点。
2. 用户能把目录树面板拖到终端左侧或右侧形成分屏，也能收回悬浮/关闭状态；分屏状态下终端本身操作不受影响。
3. 用户双击目录树中的某个目录节点后，对应终端的当前目录切换过去（本地终端立即生效；远程终端等待 shell 集成上报确认后生效）。
4. 用户能把 Obsidian 中的笔记/目录拖入目录树的指定节点，文件按 Vault 相对结构落在该节点对应路径下。
5. 用户能把目录树中的文件/目录拖到 Obsidian：无激活文件夹时落 vault 根目录，有激活文件夹时落该文件夹；同名冲突时不静默覆盖，用户能看到冲突提示并选择处理方式。
6. 在终端里执行 `mkdir`/`rm`/`mv` 等改变目录结构的操作后，已展开的目录树节点能反映出该变更，不需要用户手动点刷新（阶段一本地终端验证；阶段二远程终端在弱网下允许延迟，但断线时目录树需明确标注"未同步"而不是显示陈旧数据或报错）。
7. 阶段二（远程）在没有额外路径限制的前提下，目录树可浏览范围与该终端本身可执行命令触达的文件系统范围一致，不出现"终端能到但树看不到"的不一致。
