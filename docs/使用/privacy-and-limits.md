# 隐私说明与已知限制

面向使用者。请在开始用远程功能前读一遍——v2.0 换成了点对点直连架构，隐私模型和 V1（云端 Relay 转发）完全不同，即便你用过 V1 也建议重新看一遍。

---

## 1. 隐私

### 1.1 谁能看到你的终端内容

**没有任何服务端能看到明文。** 控制端与目标端之间是 iroh 建立的 QUIC 连接，QUIC/TLS 1.3 内建端到端加密，Termy 没有另外自己实现一层加密（也没必要）。

连接建立过程默认经 iroh 官方托管中继完成协调（几乎每次连接建立时都会短暂参与），随后尽量升级为点对点直连；直连打通后，数据不再经过中继。**无论走直连还是经中继转发，中继只按 `EndpointId` 转发已加密的 QUIC 报文，不具备解密能力**——这不是"中继承诺不看"，而是它拿不到密钥。

这与 V1 完全不同：V1 的云端 Relay 是应用层网关，业务上能够访问转发中的明文内容；v2.0 没有这样的角色。

### 1.2 没有账号，也没有任何服务端保存你的数据

v2.0 **免账号**。设备身份是本地生成的 Ed25519 密钥对，不向任何服务端注册。已配对设备列表只存在**发起连接的那个 Obsidian 插件本地**（`data.json`），不上传到任何地方。

Agent 侧也不保存任何"谁连过我"的历史记录——状态文件只反映当前这一次运行的连接状态，进程重启即重置。

### 1.3 你应该知道的元数据可见性

重连依赖 iroh 的全局节点发现网络（DNS/Pkarr）：即使连接码里内嵌的直连地址过期（比如目标设备换了网络），只要 Agent 保持在线、持续向发现网络重新发布地址记录，控制端仍可能凭 `EndpointId` 重新找到并连接它。这是一个主动的取舍——换来"连接码长期可用，不用每次重新配对"，代价是：**每次这样重连时，iroh 官方的发现基础设施在技术上能够观察到"谁在查询哪个 EndpointId"这一元数据**（不涉及终端内容，也不涉及是哪个设备/哪个人，仅仅是"这个公钥标识符被查询了"）。

如果你需要完全避免这一点，用 `termy-agent run --loopback` 起 Agent——禁用中继和地址发布，只接受本机连接，代价是控制端也必须在同一台机器上。

### 1.4 连接码等于访问凭证，请当密码对待

连接码内嵌了目标 Agent 的身份和网络地址，**拿到连接码的人可以直接向这台 Agent 发起连接**，不需要额外密码。它不是一次性的，也没有单独撤销某个连接码的机制——**唯一让某个连接码失效的方法是 `termy-agent rotate-identity`，这会让这台 Agent 当前所有连接码同时失效**，所有控制端都要用新连接码重新配对（不能只踢掉某一个人）。这比 V1"可以单独撤销某个配对码/踢掉某台设备"要粗粒度。

### 1.5 你应该做的

- 只把连接码发给你信任、且当前确实要连接这台设备的人/控制端
- 怀疑连接码泄露时，`rotate-identity` 让旧码全部失效——但要通知所有正常使用者用新码重新配对
- 不用某台设备的远程功能了，直接把 Agent 停掉（`systemctl --user stop termy-agent`），或从插件的设备列表里移除它（只影响本地记录，不影响 Agent 本身）

## 2. 已知限制

以下是 v2.0 当前版本有意接受的取舍或尚未做完的部分，不全是"不修的缺陷"——有几项是路线图里明确排在后面阶段的。

### 2.1 连接与会话

**同一时刻只允许一个控制端连接同一台 Agent。** 第二个控制端连接会被拒绝（`CONTROLLER_ALREADY_CONNECTED`），不会顶掉第一个（这点和 V1"后连的顶掉先连的"不同）。

**同一个控制端连接下可以开多个并发终端会话**，默认上限 8 个（`maxConcurrentSessions`，可配置 1–256），超出会被拒绝（`SESSION_LIMIT_REACHED`），不排队。这是 v2.0 相对 V1 的改进——V1 每台设备同时只能有一个远程终端。

**终端会话不跨连接存活。** 控制端与 Agent 之间的连接整体断开（网络问题、Agent 重启、控制端主动断开）时，这条连接下的所有会话会一并终止，包括它们发起的整个进程树。重新连接后需要重新打开终端，正在运行的命令会随之结束。

**没有测试过网络抖动下 QUIC 连接迁移能不能保住会话。** iroh/QUIC 理论上具备一定的连接迁移能力（同一逻辑连接容忍网络路径变化），但这不是本项目验证过的行为，不要依赖它。

### 2.2 文件传输：还没有

**`termy/transfer/1` 协议目前只是一个占位 ALPN**——Agent 收到这条协议的连接会直接拿 `PROTOCOL_ERROR` 关闭。v2.0 当前版本**只有远程终端，没有文件传输**，这是 Phase C 的工作,尚未开始。V1 那一套"64 MiB/256 MiB/256 个文件"的传输限制目前不适用，因为功能本身还不存在。

### 2.3 功能边界

- 目标端支持 Windows 和 Ubuntu Server（`agent/` 的编译目标）
- 控制端是 Obsidian 插件，理论上 Obsidian 桌面版支持的平台都能跑（A0 已验证 Electron 渲染进程可直接加载 `@number0/iroh`），实际验收目前以 Windows 为主
- 不支持多人同时控制同一台 Agent（§2.1 的单控制端限制）
- 没有断点续传的概念——目前连文件传输本身都没有

### 2.4 安全边界

**Agent 和远程 shell 以运行它的那个普通用户身份执行**，不提供提权。远程终端能做的事，等于那个用户能做的事——不多也不少。Windows 上进程树终止靠 Job Object，Unix 上靠进程组，都在 `agent/src/pty.rs` 里有对应实现和测试。

**连接码没有过期时间，也没有单独撤销机制**（见 §1.4）——这是当前版本刻意的简化，如果你需要"踢掉某一个人但保留其他人"的能力，目前做不到。

## 3. 出问题时

**连不上目标设备**——先确认 Agent 在跑（目标机上 `termy-agent status`）、连接码是不是当前这次运行打印的那个（Agent 重启或身份轮换后连接码会变，虽然 EndpointId 不变、旧码经发现网络也可能重新连上，但不保证）。

**连接被拒绝，报 `CONTROLLER_ALREADY_CONNECTED`**——已经有一个控制端连着这台 Agent 了，见 §2.1。

**打开第二个终端失败，报 `SESSION_LIMIT_REACHED`**——超过了 `maxConcurrentSessions`（默认 8），关掉几个不用的终端，或者到目标机上 `termy-agent config set-...` 调高上限（改的是新连接生效的值）。

**远程终端里某个命令 command not found，但 SSH 进去却能用**——目标机的 shell 配置问题，不是网络问题，见 [operations.md](operations.md) §1.5。

**目标机一直显示离线/连不上**——检查 Agent 是否在跑，以及 iroh 的直连/中继路径是否被网络环境挡住（比如严格的对称 NAT、出站防火墙挡了 QUIC/UDP）。`journalctl --user -u termy-agent -f`（Ubuntu）能看到连接尝试的日志。

**退出 SSH 后 Agent 就停了**——lingering 没启用，见 [operations.md](operations.md) §1.1。
